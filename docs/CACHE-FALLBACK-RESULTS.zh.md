# 30 秒文件缓存保底开发对照

2026-11-20。已测源码 `87a345afe6206f065236996cff60ab4e14495fd4`。[x86 与 ARM64 原生 CI](https://github.com/cuipengdba/ContainerCacheGuard/actions/runs/44683167385)。

每组使用独立新建的 cgroup v2 和独立文件。PG14 并发写入、HTTP 测试探针、2 MiB/s 物理备份、热点文件读写、每类 2500 个目录项和同父级兄弟内存压力同时存在。每组先装入 1152 MiB 普通文件页，目标文件位于 PGDATA 和备份目录之外，保留文件但退出打开它的进程。旧 vmtouch 组由上游 1.3.1 静态程序在第 30 秒单次扫描同一组授权目录，CCG 只观察。这为旧工具补了外部目录参数，实际 DBS 旧命令通常只给显式固定目录。每组只有一个回收执行者。

保底组保留 30 秒周期。开发夹具用 5 秒访问/文件保护、128 MiB 软目标、768 MiB/s 查询预算、64 MiB/s 共享建议速率和每范围每轮 1280 MiB 建议上限。真实配置示例使用更低的预算及更长保护，实际可达到的速度取决于保护状态和负载。

时间从每组开始计。SQL/API 错误均为 0。读 IO 是目标 cgroup 的合计，已剔除最初装入文件缓存的读盘，无法按单进程或路径归因。数据库和测试 API 运行在独立服务中，固定目录的实际回收数据主要来自备份范围。尾延迟反映同一开发节点上的并发测试，x86 保底组 SQL P99 较原 CCG 组升约 14%，需要重复对照和业务门槛。备份校验覆盖清单和文件内容，本试验使用 PG16 的校验器，因此跳过 PG14 的 WAL 解析。

开发环境验证了实际文件回收、再次驻留观测和真实父级 cgroup 余量变化。夹具未运行 kubelet，`kubelet_pod_available_bytes` 为 null。真实 HISDBS 的驱逐场景、业务低影响门槛及持续压力仍需结合真实信号做对照。Linux 页缓存下降和 kubelet 工作集算法中的可用内存要分别检查。临界 bounded 通过了显式开启及 OOM/脏页/回写/业务/指标失效的原生逻辑验证。上述并发对照使用默认临界暂停。

此前 CI 44681358744 首轮完整备份成功，但 x86 和 ARM64 的固定窗口回收分别到 1004 MiB 和 1008 MiB，未过本夹具 1 GiB 门槛。结果保留。最终轮保存独立原始时间序列，使用只读无 atime 的驻留测量，并调整测试压力和查询预算。最初备份用例因临时 PostgreSQL 服务的 pg_hba 未允许容器桥接地址的复制连接失败，修复限定在临时测试服务。
