# 测试报告

更新：2026-11-07。rc.9 的既有实验保留原结论；0.2.0-rc.1 新增 Web 与四容器试验，未完成项不会算通过。

## 新一轮四容器测试正在运行

在单机隔离 K3s 中，两个业务 Pod 各运行 PG18.6、对应角色的 DBS 可执行文件和 CCG；两个独立备份 Pod 各运行 PG18 客户端和 CCG，Unix Socket 连接成功。使用同一份已审计的约198GiB迁移数据分别创建可写副本，实际 SQL 对象目录为每边 1,445 个命名空间、82,392 条 `pg_class` 记录；压力表会额外增加一个关系，统计时单独扣除。四个 Pod 已在 observe 模式通过业务接口、etcd、数据库、CCG 新鲜状态和 Web HTTP 200 联合就绪检查，初始化时重启数与 OOM 均为0。

在只读源环境做的单个60秒窗口样本：DBS 约110事务/秒、447行插入/秒、2.34MB/s WAL；HISDBS 当时几乎没有写入。这不是全天分布。新实验用 `pgbench` 目标110事务/秒、每事务4行模拟 DBS 持续写入，并计划在04:00给 HISDBS 30分钟突发。15秒短测两边约6千多行成功；DBS持续写入在运行。两份备份计划03:00从独立容器以PG18 `pg_basebackup` 原生参数、60M限速执行并用 `pg_verifybackup` 校验；当前**尚未实际完成本轮备份**。

48小时采集已启动，每10秒读取四处 cgroup 指标，每12小时生成一份图表与说明，另读Kubelet Pod/事件、节点内存、业务接口。当前不足48小时，四份区间报告及不驱逐验收均未完成。内置 Web 的 Linux 单测已验证回环绑定、非回环需密钥、认证、只读API、环形历史与并发/超时配置；页面在四容器的 HTTP API 已返回200。实际 Web 长稳和前端视觉验证仍要完成。

这里的 K3s 是94上新建的**隔离单节点测试集群**，不是原生产 Kubernetes/OpenShift。原环境PG14且每容器128GiB内存限制；94为PG18、全机约30GiB。原 DBS 的生产模式缺少外围etcd/Patroni/HBP状态会主动停止数据库，所以实验保留原角色二进制、改用隔离 dev 配置与外部备份调度。不能将四Pod启动和二进制一致说成完整生产功能等价。源环境只读检查，没有改配置或触发备份。

## 真实数据实验

使用事先完整迁移、升级并审计一致的 PG18.6 数据副本：约198GiB、1428个业务模式、10217个业务物理表/分块、642157127行。新实验另外建立 reflink 副本，保留原审计基准。

测试采用独立 PostgreSQL 容器与备份/治理容器，数据库12GiB、工作容器6GiB限制。使用原生 pg_basebackup、相同96MiB/s吞吐限制、只读查询探针，分别记录源端和目标端 cgroup、驻留、IO、时间、查询延迟及 OOM 事件。

无治理全量备份基线已完成，pg_verifybackup通过；备份耗时2671.72秒，源容器file峰值11.924GiB、目标容器file峰值5.958GiB。备份结束独立mincore测得源数据目录驻留约11.414GiB、输出目录约5.743GiB；零新增OOM kill，查询探针零错误。file包含shmem，不能将此列直接当普通文件缓存。

首次完整治理对照 guard-r6 同样完成且 pg_verifybackup 通过，耗时2670.05秒，源端file峰值7.193GiB、输出5.945GiB。它**没有达到两端缓存目标**：源端自身CPU退让导致滞后，输出端脏页和临界暂停导致长期退让。改进后的 guard-r8 仍暴露异步写回后过早丢弃候选问题，约1136秒时主动中断；该轮无完整备份校验，不计通过。rc.9 增加受预算的事件处理和有限延后重试。guard-r9及提高输出预算的guard-r10均完整校验通过，最终源峰2.070GiB、输出3.193GiB；输出仍未达到≥70%峰值增量下降目标。全部数字和成本见[最终汇总](RESULTS.zh.md)。

最新重复读测试包含同一4GiB工作集两遍扫描及100Hz热点读。执行模式缓存峰值降低，但实际读盘约翻倍，热点p99从约0.038ms上升到2.823/4.686ms，**未通过低业务影响目标**。这不是可以忽略的测量噪声，也不能仅凭全量备份中的单表查询无明显劣化就宣布热页保护验收通过。不限速校验阶段输出file仍达5.758GiB；整条工作流低缓存目标未解决。

随后用相同二进制补充off/指定路径并排除热点/off三相测试：执行相file峰485.3MiB，热点p99约0.048ms、off约0.037ms，实际读盘仍为7.88GiB对4.00GiB。明确排除避免了先前数毫秒的热点代价，但没有证明≤5%相对延迟目标，也不能冒充自动识别热页。

实际恢复从最终已校验备份另建reflink副本，PG18.6启动并核对模式目录、关系目录及探针结果，通过后正常关闭。第一次演练的PG已正常关闭，但容器PID1退出连带结束内部pg_ctl执行会话，测试脚本未保存最终报告；保留该失败记录，改为从容器外确认关闭，再从新备份副本完整重做通过。启动约5.31秒只覆盖本地准备完成后的启动/连接，不含下载、解压、文件准备或应用恢复。

备份结束驻留测量与后续 pg_verifybackup 分阶段记录，避免校验读取混入备份过程指标。查询探针目前覆盖备份及校验全过程，不能把这些分位数冒充“仅备份时延”。冷起始条件只对独立实验副本发出文件建议，不执行全机 drop_caches。

模拟压力第一次进入观察相时安全退出，因为手工ctr容器没有cgroup挂载；不是将指标缺失解释为0。失败报告保留，新的独立容器补上只读cgroup视图后重跑。模拟压力读取真实PG18文件中的4GiB子集，每次64MiB/s，顺序为off/observe/paths/auto及其反向，**这不是每一相都读完整198GiB**；完整规模由全量备份实验覆盖。

pressure-r6 八相已完成：off/observe峰值约4099MiB，paths两次约421/427MiB，auto约437/422MiB；峰值下降约89%。执行相控制器采样CPU均值约单核9.6%–10.1%，RSS峰值小于10MiB；observe约1.18%，且建议量为0。这使用100ms/秒工作预算、1GiB/秒查询覆盖等高吞吐实验配置，不是默认参数，也没有达到“执行成本始终≤单核5%”的设想。此前r3/r4/r5未达预期的较差结果保留，不能只报告最好一轮。

单独8GiB写入探针用32个256MiB文件模拟96MiB/s输出。调整临界策略、脏页阈值、无效冷却和速率后，峰值从3.90GiB降到1.70GiB、结束驻留约492MiB；这是零填充写入探针，不代表真实全库备份已经通过。

这里复用的是真实迁移 hisdbs 数据，DBS 的备份/同步访问形态由实验模拟；没有宣称已运行完整 DBS 业务二进制，也没有独立迁移另一份 DBS 数据。该实验不是生产负载重放。

约198GiB是真实迁移副本的规模，不能写成已经覆盖典型1.5TB。查询探针是一张实际表的只读聚合，不代表所有读写业务，也没有在本轮运行同机etcd/Redis/Prometheus压力源。未出现这些服务的异常没有被当成验收依据。
