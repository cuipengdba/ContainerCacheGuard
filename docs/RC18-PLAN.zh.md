# rc.18规划：同容器统一缓存治理与真实保护信号

日期：2026-11-17；需求C039。用户要求规划下一版，并将数据库与备份保留在同一容器。本轮仅规划、修订文档和同步GitHub，**不开始产品编码、发布或服务器实施**。当前已发布候选仍是0.2.0-rc.17，VERSION不变。下面新增接口及验收数字均为设计草案，不是现有CLI能力或已完成结果。

## 1. 本版最重要的变化

DBS、HISDBS各保留一个原业务容器，容器内继续运行数据库、DBS管理程序、备份/校验/同步工具和一个CCG。取消新建dbsbackup/hisdbsbackup容器的要求。部署细节以[同容器架构](SAME-CONTAINER.zh.md)为准，旧四容器说明和已发布的历史测试仍保留时间背景。

目标是：**同一资源预算下，先减低复用输出缓存的影响，再审慎处理源端文件页；优先看业务和真实节点余量，不以清掉多少缓存作为唯一成绩。** 同容器不是IO隔离，memory.reclaim也不能区分备份页与业务热点。保留已有PG14工具、DBS调度和限速，不借升级容器布局自动修改CPU、内存、IO及数据库参数。

## 2. rc.17已有与rc.18补齐的差距

| 事项 | rc.17已发布能力 | rc.18计划 |
| --- | --- | --- |
| 源与输出路径 | 可指定多个根，但共用全局策略 | 一个CCG内给目录声明角色，独立保护/排序，共享总预算 |
| 压力归因 | 根目录/文件类型覆盖、驻留查询、候选事件和cgroup指标 | 补充任务阶段、路径角色与共享计费说明，防止重复统计 |
| 备份/校验状态 | 不接管DBS，不自动识别全部任务 | 接收可信任务信号；可选只读PG进度适配，已验证的工具包装方式 |
| 节点保护 | 内核后端有schema2契约，生产采集器尚未验收 | 交付可运行的可信节点采集接入及版本适配，保留原始时间/来源 |
| 无PSI环境 | 显式实验门槛，缺少真实盘端到端证明 | 关联真实块设备、业务探针和队列/延迟，先验证输出路径；源策略不自动降级 |

## 3. 单容器一个控制器，路径有区别但预算只有一份

拟为`paths`和`auto`都提供路径角色覆盖：自动发现不增加未授权根；显式角色定义覆盖已验证根中的策略。至少包含以下角色：

| 角色 | 默认策略方向 | 必须避免的误区 |
| --- | --- | --- |
| backup-output | 在不再改写、完成必要保护期、明确低复用后优先 | 不按“文件刚关闭”就认定冷页；校验/压缩/上传可能还会读 |
| database-source | 保守扫描、更长保护、受控数据文件例外与热点排除 | 不把base下全部文件都当冷数据；执行位例外只限授权数据路径 |
| excluded | WAL/事务目录、CCG状态日志、密钥、运行文件等不进入文件建议 | 排除只约束文件后端，不能承诺约束内核reclaim |

备份源、输出、索引和日志的inode可能通过挂载别名或硬链接重叠。注册时核对规范路径、挂载、设备、inode、权限与执行位；运行前重验。冲突不允许采用更激进策略；角色冲突拒绝或按更保守规则处理，展示原因。表空间真实路径须另行授权，不放宽符号链接规则。文件数量多只是待核实的覆盖/成本因素，不直接当成缓存上涨根因。

控制器保留单工作队列和全局CPU/RSS、工作时间片、打开次数、扫描/建议字节预算。角色额度必须取全局剩余量，不能为每个路径复制一份额度。为源端保留有界轮询机会，避免大备份目录永久挤掉源端覆盖；索引/事件溢出明确计数并退回有界轮询，不能无限补扫。

按角色记录“允许范围内的已知文件/跳过原因、唯一/重复查询、驻留、合格候选、建议、复查、重新驻留、延迟/终态”。唯一性有窗口和淘汰上限，不能声称全量精确驻留；目录驻留不能同容器file总量简单相加，也不能把累计扫描字节当实际覆盖率或释放量。

## 4. 让控制器知道备份做到哪一步

拟支持`idle / backup / verify / compress / transfer / sync / restore`等可信任务阶段。多个任务可并行，活动集合必须有界；“备份和校验同时发生”不能被一条最后状态覆盖。任务信号缺失、乱序、过期或冲突时，阶段显示unknown并采用更保守文件策略，不假定任务已经结束。

接入顺序：

1. 优先使用DBS已有、已验证的任务开始/结束和状态文件接口；只读统计`pg_stat_progress_basebackup`可帮助识别备份，但不能识别全部校验/同步，更不能把无进度行当作所有任务完成。
2. 若没有可靠信号，可选设计备份命令包装器/回调发布阶段。显式传参，不拼shell字符串；完整保留原工具参数、退出码、stdout/stderr、信号转发和原有清理行为，不能把失败改为成功。CCG不自动kill数据库或暂停WAL流。
3. 一般容器不依赖PostgreSQL插件；未知工具可用通用任务信号。无任务信号仍可按保守路径策略观察，不把它变成强制备份依赖。

信号字段草案包括schema/version、实例、任务ID、阶段、源/输出根、原始时间、序号、进程启动身份和退出状态。单纯PID/进程名或命令行字符串不能充分证明身份；不把凭据/完整SQL/敏感参数写日志。读取须有大小/条数/深度/超时限制、权限检查和抗符号链接措施；控制消息不能扩展授权根或放宽业务保护。

verify/restore期间优先保护被读取的数据，不为了压缓存迫使它反复读盘。路径级停让不等于内核调用被路径约束；紧急内核资格仍单独检查整个容器。

## 5. 真实信号闭环，尤其是无PSI机器

### 5.1 节点和驱逐口径

计划在同一静态二进制中增加一个**可选的节点信号采集子命令**，由节点侧现有管理方式运行；具体命令名与接口开发时定稿。普通文件后端不强制安装节点特权服务，生产内核救援需要相应真实信号。采集器可与reclaim-agent同节点部署，但不变成备份容器或Web服务。

从部署环境选择受认证、只读的kubelet/节点数据与有效驱逐配置。按实际Kubernetes版本适配node和allocatable口径，保留源时间、boot/cgroup身份、配置指纹；硬/软阈值及禁用状态不能由“缺失”推断成0。不得关闭TLS验证、输出凭据，或把宿主MemAvailable拼成真实kubelet值。权限、API或时间不满足时，产出明确不可用状态。

schema2继续校验来源和业务采样覆盖；兼容已有schema1消费者需要明确适配层，不能把版本号改成2就通过。节点信号过期、时钟回退、配置变更、快照不一致均停止相关新请求，保留诊断。

### 5.2 共享磁盘与替代信号

核对源、输出、状态日志路径的实际挂载及块设备，处理bind/PVC、overlay、设备映射与多磁盘。对能确认的逻辑/物理设备读取计数并计算区间IO、await及队列；同时保留各层身份，避免父子设备重复相加。映射不清、多设备/NFS等不支持时显示unknown，不能自动挑“最大分区”替代，也不自动写盘标定。

低IO不证明冷页。无PSI实验仍需真实SQL/API延迟、足够样本、错误率、脏页/writeback、文件refault与实际节点余量共同允许；信号原始年龄、采集开销和覆盖缺口单独报告，替代输入不宣称与PSI等价。

**混合容器不能全局切到宽松策略来处理PGDATA。** 对备份输出的实验资格只授权该路径；源端缺保护时继续观察/暂停。rc.18需要实现逐角色资格判断，内核后端则仍独立检查整个cgroup。无PSI内核单次128MiB上限及显式实验开关不因本版改架构而放大。11月12日94“无PSI”是历史只读结果，本轮没有复查，不推断当前配置完全不变。

## 6. 保留memory.reclaim，但不把它当主清理循环

登记目标从四个业务/备份cgroup改为两个业务叶子cgroup。文件后端优先输出；内核请求不能再标记为“只回收备份”。节点级串行、30秒间隔、5分钟1GiB请求额度、先停让文件队列、一次尝试、持久journal、阻塞辅助进程、看门狗和真实退出后释放占用都保留。

一次事件按boot/cgroup身份管理，**备份任务ID改变不得重置事件**。EAGAIN可能已有部分收益，不补刷；进程重启、配置路径变更、调用结果未知不消除历史。容器/可见父级与真实节点需持续恢复才允许下一事件；历史OOM的解释和处理仍需明确流程，不增加“忽略历史”或“强制清零”开关。保留1/5/30/120秒实际复查。

两个业务目标同属数据库保护等级，计划按有效风险和等待时长公平调度；不把“DBS/HISDBS谁先登记”永久当成更高业务优先级。此公平调度是rc.18待实现，rc.17的priority仍是已有容器级静态参数。默认内核后端关闭，不自动更改memory.max/high/swap、CPU/IO或Pod资源请求，不创建/移动业务到新子cgroup。

## 7. 参数草案和日志

以下仅为字段设计，不是可直接传给rc.17的配置。开发时要统一命名、默认值、校验和兼容迁移；未知新字段仍应报错，不能静默忽略。

| 拟新增/调整项 | 人话解释 | 约束 |
| --- | --- | --- |
| 路径角色集合 | 哪个是数据库源、哪个是输出、哪些排除 | 有界、绝对路径、身份重验、冲突更保守 |
| 角色保护期与调度份额 | 输出先处理，源端更谨慎但不永久饥饿 | 不突破全局预算/保护，份额不是内存硬限额 |
| 任务信号来源与最大年龄 | 备份/校验做到哪一步，何时不再信任状态 | 默认不猜测完成；只读/回调明确区分 |
| 活动任务与事件记录上限 | 防止任务多导致控制器自身膨胀 | 溢出计数，不无限队列，不自动放宽授权 |
| 节点/块设备采集周期和来源绑定 | 让紧急操作有真实输入 | 区间时间、身份、缺失和配置版本可追溯 |
| 事件快照输出策略 | 关键时刻完整，平时用小摘要 | 不丢唯一尝试/错误证据，不引入Web |
| 每角色统计与日志版本 | 看出扫哪里、为何跳过、哪类有效 | 对离线report/compare保持可识别的版本兼容 |

配置仍可生成默认auto/paths，先observe；特殊路径显式覆盖角色，不为普通容器强加数据库名。一个控制器统计全部自身开销；如果有节点采集器/agent及辅助进程，验收单独测量后再汇总，不能只测CCG主进程。

每天一个日志文件、30天/1GB自动清理和无Web约定保留。逐秒重复完整内核前后快照可能产生额外缓存/IO，计划改为关键事件持久记录加周期引用；不得将可观测性优化变成删除OOM历史或未决journal。小时图包含缓存、真实驱逐余量、任务区间、回收调用点、IO和SQL/API，不只画“下降越大越好”。

## 9. 验证设计与初始验收门槛

### 9.1 测试场景

1. 独立开发机：至少1GiB已知合格低复用缓存；同容器同时有数据库样式源、输出、mmap热点与普通日志。验证PGDATA及大文件确实被覆盖，驻留不冒充冷热。
2. ≥4GiB缓存池：请求默认值与较大值分别做对照，限定内存/IO，不通过重启数据库归零；记录实际下降、延迟复查、重新驻留和无收益。内核大请求未验证前不扩大生产默认。
3. 故障压力：父级内存/脏页、共享磁盘竞争、缺PSI/错误权限/错设备、信号过期和时钟回退、目录/提示/任务溢出、备份失败、CCG/agent重启、在途未知。业务/保护否决优先。
4. 94真实PG14：先盘点并另行实施同容器布局，核对源数据时间点、模式/表数量、数据量、PG参数、扩展和备份链；只读采样171需保持原有授权边界，禁止在171测试/改动。负载模拟目标是速率、事务/查询结构和延迟分布相近，不能承诺与171逐请求完全相同。
5. 配对A/B：同数据和压力、配额/备份参数、冷热初态及阶段一致，重复并平衡先后顺序；分别比较现有DBS vmtouch/nocache方案与CCG。并存仅作观察，不作收益归因。备份、校验、同步单独与重叠都测，不drop_caches、不重启归零。
6. 持续运行：完成小范围/高压安全门槛后再做48小时，每小时离线图和说明覆盖实际采样窗口；本轮不创建自动任务或启动48小时计时。完整校验加独立目录恢复启动，检查真实对象/数据，不把工具退出0当恢复演练。

### 9.2 规划门槛（不是实测结果）

| 类别 | 初始验收规则 |
| --- | --- |
| 安全与范围 | 源文件内容/备份校验保持正确；同一数据范围只有一个执行权威；无越权或隐式扩大路径；内核每事件最多一次尝试 |
| 文件回收机制 | 使用初始驻留≥1.125GiB、其中已知合格≥1GiB的低复用夹具，目标120秒内夹具文件范围净下降≥1GiB，随后120秒复查仍维持；容器总量另列，热点/脏页场景不强行达到此数值 |
| 内核回收机制 | 请求R与实际下降分开；较大已知合格测试池初始目标为120秒末普通文件净下降≥0.75R；失败记录原因，不为达标补刷或降低保护 |
| 业务代价 | 等压重复对照SQL/API错误0；P99相对上升暂以≤10%为开发筛选线，同时必须满足事先填写的绝对SLO，不能靠宽松基线通过 |
| 资源代价 | CCG容器内主进程暂沿用单核CPU≤5%、RSS≤128MiB候选预算；节点采集/agent/辅助进程总成本与物理盘IO峰值单列，阈值实测前填写，空值不通过 |
| 实际缓存收益 | 对同等备份阶段比较普通文件峰值与时间积分，初始候选目标降低≥30%；若原基线接近零或占用主要是anon/shmem，标为不可适用并诊断，不伪造改善百分比 |
| 驱逐与OOM | 48小时有完整真实节点/allocatable采样，OOM/驱逐/非计划PG重启新增均0；未知/缺采不算0。即使通过，也仅证明该测试窗口和压力范围 |
| 备份恢复 | 实际数据量在约定≤24小时窗口完成且完整校验、独立恢复成功；RTO及IO峰值上线前先定数值，未定义不算整体通过 |

以实际数据量D和备份、校验、同步及恢复的额外耗时估算吞吐余量，不能把300MB/s标称速度当安全速率，也不能把`--max-rate`等同于共享盘总IO限速。阈值须写进试验记录，改动后说明原因并重新配对；安全否决项不能为追求缓存数字放宽。

## 10. 发布和回退

仍交付一个静态Go二进制的linux-amd64/linux-arm64版本，CLI兼容旧配置，无Web；可选子命令不要求Python依赖或安装PG客户端到CCG内。PG14工具由原DBS环境提供。新版配置先离线检查，再独立状态observe，小范围enforce，最后才做内核灰度；发布附件记录真实源码/测试范围与SHA256。

回退只换CCG和相应配置，不重启数据库；停止新请求后确认辅助进程真实退出，持久journal不删。旧DBS清理恢复前确认CCG同范围已退出；备份原调度/输出及已有有效备份保留。旧备份容器退役是部署迁移任务，不能因文档改了便直接删除服务或存储。

## 11. 依据与证据边界

- [PG14 pg_basebackup官方文档](https://www.postgresql.org/docs/14/app-pgbasebackup.html)：复制协议、进度与限速语义。
- [Linux cgroup v2官方文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)：整体计费、IO控制、memory.reclaim可能多/少回收；实际能力仍按现场内核接口核对。
- [Kubernetes节点压力驱逐官方说明](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)：节点/allocatable及inactive_file口径；部署实现按实际版本验证，不套用未核实的新版本特性。
- [rc.17实际交付](RC17-DELIVERY.zh.md)：短时隔离实验不等于真实驱逐验收，旧四容器结果不直接外推到本版同容器方案。
