# rc.13开发建议：受限环境回收与可信的多容器报告

日期：2026-11-11。状态：应用户“规划下一个版本”形成的计划，**尚未开始rc.13编码、发布或现场操作**。代码基线为已发布rc.12（f980817），最新发布和71项顶层race单测/32项CLI每架构的实际结果见[交付记录](RC12-DELIVERY.zh.md)。本计划不表示新能力已经可用。

## 本版要解决的问题

1. rc.12能解释保护输入缺失，但不能在缺PSI时自动形成经过验证的替代策略。94最后核验于2026-11-10：内核支持PSI但默认关闭，四实例均缺IO PSI；这不是本日现场重新采样的结论。
2. report当前要求每次只处理一个实例的日志。不同容器可能看到相同cgroup路径，PID也可能复用；同PID生命周期事件虽已处理，缺事件的旧日志仍有身份盲区。
3. 新等待索引微基准和代码回归已经通过，但真实业务下的缓存改善、额外读IO与尾延迟仍缺完整证据。已有匿名内存尖峰不能靠文件页建议释放解决。

本版目标是补齐受限环境的策略和可信数据基础，再做真实备份输出对照。不会以新增参数数量或累计建议字节数判断成功。

## 建议范围与优先级

| 优先级 | 工作 | 增加的能力 | 完成依据 |
| --- | --- | --- | --- |
| P0 | 显式受限保护方案 | 保持原严格策略默认值；新增需要明确选择的无PSI受限方案，第一阶段仅面向paths指定的低复用备份输出 | 缺失、过期、错误来源、身份变化和任一风险超限都拒绝新动作；输出完整保护清单与缺口，不静默改阈值 |
| P0 | 实例和运行标识 | 配置稳定instance_id，每次启动生成run_id，记录可取得的目标cgroup身份；状态、每日日志、预检与报告一致携带 | 同PID复用、同cgroup路径、日志截断、跨Pod重建均能正确断开基线；身份不充分不自动合并 |
| P0 | 可比较的效果验证 | 输出端先行，匹配数据、备份限速、业务压力和缓存起点；对观察、严格策略及受限策略分别归因 | 完成实际全备、校验和隔离恢复，比较缓存峰值/面积、重新读盘、尾延迟及备份耗时；失败和停压保留 |

## 无PSI方案的边界

这里的“受限”表示已知保护能力减少、动作范围和预算更小，不等于与PSI等价，也不是对原策略的静默自动降级。

- 严格策略的默认行为和原配置兼容性保留。显式选择受限方案时，由配置验证、doctor和状态共同说明所选保护及未覆盖能力；不能仅把PSI阈值设为0就称为已解决。
- 第一阶段只评估cgroup v2、paths模式、声明为低复用备份产物的范围。声明不能证明文件是冷的，原文件安全检查、改写保护、驻留复查和再次驻留退让仍保留。auto范围及业务PGDATA不在首阶段放开。
- 替代前提至少包括：有效的当前内存分类/脏页/写回/OOM计数、连续IO与refault速率、来源明确且新鲜的节点余量和业务延迟信号，以及自身CPU/RSS。共享底层盘场景还要明确磁盘/同机服务信号的覆盖范围；仅备份容器自己的IO不能代表整块盘的压力。
- 首样本、差分基线失效、任一必需信号缺失/过期/非有限数、时间倒退、采样空窗、来源变化均拒绝新建议。信号恢复仍经过现有连续健康等待，不能因为切换方案跳过预热或放大额度。
- 先使用较低的建议速率和工作预算，具体值在测试前记录。高脏页、明显重读、业务延迟和节点余量风险触发退让；不为保持回收量而提高预算或绕过停压条件。
- 节点信号与业务信号可由独立只读采集器以受限文件输入，协议需包含时间、来源身份、单位和有效性。核心进程不必获得集群管理员权限，不默认读取全机所有cgroup，不通过执行任意命令获取指标。现有简单SQL连接探针不能充当完整业务p99。

PSI度量任务因资源争用而等待的时间，IO字节速率不直接表达同一件事；因此替代方案属于本项目的待验证设计，不能从接口存在推导安全。[内核PSI说明](https://docs.kernel.org/accounting/psi.html)支持这一差别；[cgroup v2接口](https://docs.kernel.org/admin-guide/cgroup-v2.html)用于核对每项输入的实际语义。参考机制的描述不代表94已经具备或启用它们。

若94能安排维护启用PSI，应另立宿主变更和回退安排，再验证严格策略。本规划不修改启动参数或重启。若替代信号也不具备，正确结果仍是观察/暂停，而不是勉强放行。cgroup v1的受限执行不承诺纳入本版，原有观察和诊断兼容性保留。

## 实例标识与报告设计

- instance_id标识一次部署中的逻辑实例，四角色分别设置，并在跨节点汇总时保证命名空间唯一；默认单实例运行不因未配置该字段而失效。没有可靠instance_id时，多实例合并必须拒绝或要求显式来源映射。
- run_id每次进程启动重新产生，不能仅由PID拼接；离线增量报告遇到run_id变化即断开计数和时间基线。状态/日志的新增字段保持旧消费者可忽略的兼容方式。
- cgroup设备/inode等可见信息只用于识别目标变化，不能代替跨主机唯一身份；无法取得时标未知。报告同时记录采样范围和来源，不把同名路径视为同一容器。
- rc.12及更早日志允许继续单实例报告，但要注明旧字段限制；不能伪造run_id后声称补齐了旧数据身份。
- 图片首选SVG，避免在守护进程里增加字体渲染服务；直接PNG输出作为后续字体授权/体积评估项，不列入本版必须交付。SVG是离线文件，不启动Web页面或监听端口。
- 图中分开显示普通文件、匿名、共享内存、节点余量、IO与工具成本；覆盖哪些独立业务指标必须列明。缺样不补成0，未接入的OOM/Evicted/备份结果标未知，不能仅凭CCG曲线显示“业务通过”。
- 小时图片的生成可由既有外部采集流程调用。开发图片输出不等于已启用定时任务，也不替代先前每小时现场汇报的交付工作。

## 验证顺序

1. 先完成策略及输入协议，明确严格/受限选择和旧配置兼容；再编码。保护缺项不能被模式选择意外绕过。
2. 在隔离数据测试信号失效、恢复、身份变化、脏页与热点反复读入，验证建议停止、已有反馈及预算边界；不调用全机drop_caches。
3. 原生amd64/arm64完成vet、race、CLI、静态ELF及无HTTP、日志30天/1GB回归。旧版本计数不能当作本版实际结果。
4. 94现场操作前刷新基线，复核PSI/替代信号和匿名内存风险，确认可承受的压力档位及停止线。工具版本升级不能被当作已获批准的宿主维护或停压任务恢复。
5. 对每个输出端先观察，再只启用该输出端进行交错对照；优先单库备份，稳定后评估两库组合。固定备份限速、数据与压力；不能固定的缓存起点和并发变化写进报告。保留既有vmtouch/nocache调用的状态以免混淆归因。
6. 两库分别完成新全备、pg_verifybackup、隔离恢复和对象/业务抽查。业务源PGDATA回收另列实验，不由输出端成功推断。
7. 完整对照和配置稳定后才开始48小时。48小时、YsP正式服务及旧迁移/等压任务继续追踪，不因新版本发布改为完成。

Kubernetes驱逐涉及节点级信号、阈值与Pod选择，本地文件页下降不能证明不会驱逐。[官方节点压力驱逐说明](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)用于界定这一点；宿主MemAvailable也不能直接冒充Kubelet的memory.available。

## 建议验收线（规划值，尚未达到）

这些数值是试验前讨论的起点，需要根据可测噪声、真实业务SLO和94容量写定，不能试验后为了通过而调整。

| 项目 | 建议起点 |
| --- | --- |
| 文件缓存收益 | 对基线确实高于软目标的输出端，配对窗口采样峰值下降至少20%，同时展示缓存随时间的面积/持续时间；低于目标的基线以低开销和不必要动作数评价 |
| 备份与额外读IO | 完整备份耗时增幅不超过10%；匹配业务窗口额外读字节增幅不超过10%，共享盘和校验阶段分别解释 |
| 业务延迟 | 两库及实际覆盖的同机业务p99增幅建议不超过5%，同时满足其绝对SLO；没有有效业务p99则该项未验收 |
| CCG成本 | 每实例运行窗口平均CPU不超过单核3%、RSS不超过128MiB作为初始预算；同时给出短时峰值、FD和队列趋势，不将反馈阈值称为硬限额 |
| 完整性与连续性 | 新全备、原生校验、隔离恢复成功；无新增OOM/Evicted、非预期PG重启或业务错误。停压、中止和无指标均不能作为通过 |
| 报告可信度 | 不串容器/运行，不跨缺样桥接计数，不把建议量当释放量；旧日志限制和来源覆盖清晰 |

## 发布与交付门槛

rc.13源码、静态双架构程序、详细中文手册、模板及机器可读回归结果独立发布，标签与通过CI的源码和附件摘要一致。发布说明必须分开列代码已验证、现场已验证与未完成事项。

受限方案只有通过输入故障回归及94输出端完整配对试验后，才能标注为该场景下已验证；若现场前提不足，可保留为观察/实验能力，发布说明不得称已经解决驱逐。不将48小时、ARM64 64KiB页或CentOS7实机验证凭空标为完成。

本次只做规划；171不操作，94不修改。PG14目标、无Web、静态双架构、每日详细日志和30天/1GB保留。视频及领导长期方案继续暂停。
