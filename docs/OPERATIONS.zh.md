# 从问题诊断到长期治理

这份文档面向需要部署、排障和汇报的人。当前程序管的是普通磁盘文件页缓存；它能降低指定负载带来的缓存积累，但不能替代内存容量、磁盘隔离和 Kubernetes 资源规划。具体数字以[测试报告](TESTING.zh.md)为准。

## 1. 用证据还原问题

物理备份可以拆成两条通路：数据库服务端读数据文件 → 文件页进入内存；备份客户端接收数据 → 写输出文件 → 脏页、写回和干净页缓存。数据库与备份客户端分别在两个容器时，两端都要观察。同一块磁盘还承受业务查询、日志落盘和同步，限速只解决其中的吞吐约束。

同事观察到备份与同步错开后仍出现缓存增长，说明单项工作也可能超过资源余量。清理 PGDATA 后暂未再驱逐，是文件缓存参与问题的证据，尚不能单凭这一点排除其它原因。1200 万和5000万条/天的差异，应同时记录保留天数、表/文件数、业务并发和实际扫描字节数。

| 观察 | 可以支持的判断 | 还不能推出什么 |
| --- | --- | --- |
| file、active_file 上升 | 文件页及活跃列表值得重点跟踪 | 内存全是可立即丢弃的冷缓存 |
| 文件很多 | 目录遍历、inode/dentry和控制器发现成本可能增加 | 文件数是唯一根因，合表就一定解决 |
| vmtouch 后曲线下降 | 其中有可接受释放建议的文件页 | 没有后续重读成本 |
| limitbk_io 已生效 | 备份吞吐有边界 | 两端缓存有硬上限、全部磁盘 IO 都受同一限制 |
| requests 较小的服务先被驱逐 | 资源配置与排序有关 | 只提高 requests 就消除了节点压力 |
| 没有 OOM kill | 本次没有该类内核终止事件 | 没有 kubelet 驱逐，或已证明长期稳定 |

Kubernetes 官方文档明确指出：Linux 驱逐计算将 inactive_file 视作可回收，而 active_file 的增长可能被计入内存压力。因此，要看 kubelet 的 memory.available、实际事件和版本，不能拿容器里的 free 或单独一个 file 数字代替。[节点压力驱逐](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)

## 2. CCG 相比现有工具的区别

| 比较项 | 定时调用 vmtouch | nocache 包装进程 | ContainerCacheGuard |
| --- | --- | --- | --- |
| 主要作用点 | 命令指定的文件范围 | 被包装进程及适用的动态链接文件操作 | 独立常驻，可见且获准的文件范围 |
| 独立数据库后端 | 脚本另行指定 PGDATA | 包装客户端不会自动注入独立数据库进程 | 同容器或共享同 inode 的只读卷 |
| 预算与压力判断 | 需要脚本另外实现 | 不等于容器压力控制器 | 内置字节、发现量、时间、自身资源、脏页和业务信号限制 |
| 反馈 | 需要另外采集并关联 | 关注文件生命周期及已有驻留 | 建议量、观察下降、再次驻留、无效与延后重试分别记录 |
| 热页识别 | 不应把驻留当热度 | 有自身机制及覆盖边界 | 保护期与反馈，仍不能精确证明冷页 |
| 成本与局限 | 重复全目录处理可能有峰值 | 拦截和额外检查也有成本 | 常驻索引有内存成本，预算不足会滞后 |

vmtouch 还有驻留诊断、触页与锁页能力，不能把它简单描述成只有一次性清理。nocache 也并非仅适用于复制某几个文件；限制来自拦截机制、进程关系及调用路径。复制协议本身不是“共享内存直接传输”。[vmtouch](https://github.com/hoytech/vmtouch)、[nocache](https://github.com/Feh/nocache)

这些控制逻辑理论上也能写进复杂脚本。CCG 的价值是统一实现、结构化状态、受约束的操作和可复测的行为，不是声称发明新的内核算法，或保证每个场景都优于已有工具。

## 3. 短期措施

继续保留已确认有效的备份吞吐限制。按任务实际结束时间设置错峰与互斥，而不是只把两个开始时间间隔一小时；任务超时和积压也要记录。按实际驻留与业务代价确定清理范围，不把 PGDATA 中所有页都视为低价值。

先部署 CCG observe，核对 roots、目标 cgroup 和 unknown/degraded。进入 enforce 验证时，停用同一范围的旧清理任务，保留单一执行者。停止旧清理的方式应通过受支持的 DBS 配置或经验证的接入改造实现，不能把 vmtouch/nocache 偷换为返回成功的空命令。

不要只压低 memory.high 后就结束工作。它触发的是整个控制组的回收压力，可能连带重读或写回。若要与 IO 控制配合，先确认宿主实际内核、cgroup 版本、设备映射和读写归属，再做独立对照。CCG 不自动写这些参数。

## 4. 工具层方案

每个明确的资源归属使用一份配置。数据库源目录使用较长保护、热点排除和保守的临界暂停；低复用备份输出目录可以使用经写入实验验证的脏页阈值、较短无效冷却及 bounded 临界策略。两者不应盲目复制同一组参数。

控制过程是：发现一小批文件 → 查询有限范围是否驻留 → 等待保护期 → 检查资源与业务条件 → 发出有额度的建议 → 复查下降与重新驻留。部分页面因写回暂未释放时，保留候选、延后有限次数重试，避免每次都等待全库重扫。候选耗尽次数后回到常规发现，不无限堆积重试。

软目标不是硬上限。保护期、写回延迟、内核拒绝建议、发现滞后、索引预算和热点保护都可能使缓存高于目标。若持续高于目标，状态必须解释原因，处理者应减小输入压力、调整经验证的预算或增加资源，而非只追求更大的 advice_bytes。

可以用一个近似关系理解控制是否跟得上：**缓存变化速度 ≈ 新进入缓存的速度 − 内核自然回收速度 − 治理产生的有效下降速度**。这里不能拿建议字节数直接当有效下降，更不能把网络传输量当两端精确缓存增长量。若输入长期大于有效回收，哪怕每秒都有“释放成功”的日志，缓存仍会涨满。

还要给反应时间留空间。例如60MiB/s的缓存增长，等待30秒就可能多积累约1.76GiB；学习期、目录发现和文件保护可能有重叠，不能机械相加，但也不能忽略。常驻程序应提前运行和核对范围。严格限制CPU、保留较长保护期和要求缓存几乎不上涨，三者在高吞吐场景可能无法同时满足；实测决定需要多少预算、是否降低输入或实施资源隔离。

输出持续写入比只读源扫描更难：第一次建议可能仅启动异步写回，后续还要复查和重试。因此源端能跟上，不代表同样的工作预算也能处理输出端。参数调优要同时展示CPU、脏页、建议量、观察下降、实际IO和业务延迟，不能把多花资源得到的改善隐藏起来。

rc.9已经实际暴露热页保护的局限：重复扫描叠加热点读时，缓存下降伴随读盘约翻倍、热点p99明显升高。不能据此默认对全部PGDATA开启高强度auto enforce。应优先治理明确低复用产物，对可识别热点使用exclude_paths；PG文件会随重写等操作改变，排除名单也需要维护。无法可靠确定范围或业务代价时保留observe，并采用吞吐约束、容量或隔离措施。保护期及反馈不等于内核级冷热识别。

全量备份后的pg_verifybackup也是独立读取负载，不继承pg_basebackup限速。实测该阶段仍使输出file升至约5.76GiB。规划预算必须覆盖备份、校验、合并、同步与恢复各阶段，不能只治理其中一条命令。

## 5. 架构层方案

长期优先消除关键服务与大吞吐任务争用同一底层资源的关系。评估独立备份存储、独立备份节点或由合适的数据库副本承担备份。只拆成两个容器、但仍使用同一块磁盘和同一节点内存，不能获得物理隔离。

按业务峰值、必要热点、系统预留和备份余量规划 requests/limits；不要用优先级调整掩盖整体容量不足。副本备份还需校验复制延迟、WAL保留、切换行为和恢复链。快恢复可保留本地已校验的恢复集，但本地快速副本不能代替独立故障域中的备份。

CCG 不接管备份/恢复。PG18 原生备份、增量合并和校验流程继续由上层负责；任何缓存治理方案都应经历完整恢复启动和业务核对。只通过文件校验还不足以覆盖应用依赖和恢复操作流程。

## 6. 验收与回退

| 维度 | 建议判据 | 需要保留的证据 |
| --- | --- | --- |
| 效果 | 相同负载下，缓存峰值增量降低≥70%作为实验目标；生产绝对预算另定 | 两端起点、峰值、末值、file/shmem/active/inactive、独立驻留观测 |
| 业务 | p95/p99 劣化≤5%、吞吐下降≤3%作为待定标目标；微秒级探针需考虑测量噪声 | 相同窗口和查询，错误数、请求量、磁盘时延 |
| 自身成本 | 按公开配置给出均值、峰值和持续趋势，不用“零开销” | CPU以单核百分比、RSS、FD、索引、日志量 |
| 数据 | 原生校验通过，恢复启动及业务核对通过 | 校验退出码、恢复日志、对象/数据比对 |
| 集群 | 无新增压力驱逐，节点余量高于业务选定的警戒线 | kubelet信号、事件、配置和足够长的业务窗口 |
| 异常 | 暂停、退出、指标缺失和身份变化时停止新增建议 | 状态原因与计数，业务继续运行 |

先在隔离副本验证，再小范围上线，最后扩容。出现业务延迟、重读、持续写回或治理成本超预期时先 SIGUSR1，必要时 SIGTERM。暂停不会恢复已释放的缓存；允许业务自然重新建立热点，避免全库强制预热。保留配置、版本、日志和失败试验，不只保存最好的曲线。
