## 真实内核实验：一次请求后的下降能否维持

只在GitHub原生临时虚拟机新建2GiB叶子cgroup，装入1.125GiB已知闲置、低复用文件缓存。保持数据库运行，普通文件后端设高软目标避免混入释放；内核后端请求256MiB。没有改运行器既有cgroup限额、全机drop_caches、重启数据库或清零OOM。新建测试cgroup限额是实验隔离，不是修改业务限额。

| 架构 | 初始文件缓存MiB | 请求MiB | 120秒末容器净下降MiB | 文件净下降MiB | 生命周期耗时ms | 请求登记次数 | OOM |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| amd64 | 1152.00 | 256.00 | 243.31 | 250.00 | 7.98 | 1 | 0 |
| arm64 | 1152.00 | 256.00 | 243.04 | 249.93 | 7.26 | 1 | 0 |

耗时是持久登记开始到辅助进程真实退出，包含提交/启动开销，不是独立测得的纯syscall时长。容器净下降基线是夹具装入后，包含CCG随后运行的内存；缓存下降是可观察净变化，不能把所有变化严格归因于一次调用。CCG自己的日志/状态也会产生文件缓存，本实验1秒日志频率高于默认10秒。

两架构均真实终止再启动执行器，持久记录保持一次，不会因重启再发请求。1/5/30/120秒均获得复查；agent每秒采样，复查实际可能迟到，原始时间完整保留。120秒末文件缓存约902MiB，未重新涨回初始1152MiB；没有把“请求256MiB”写成“准确释放256MiB”。

**node信号刻意使用合成测试值，验证的是实际容器cgroup触发与内核操作，不是kubelet驱逐。** 节点值没有作为回收收益计数；不能由此声称提高了真实节点驱逐余量。实际内核回收的单次256MiB有证据，配置允许的更大请求及4GiB以上池实验仍未验收。

## SQL/API和IO代价

PG14探针连接真实数据库，本地测试API执行真实查询；这是小探针，不是DBS/HISDBS实际业务重放。每个阶段长度和样本数不同，P99只是采样统计。

| 架构 | SQL P99 基线→内核阶段ms | API P99 基线→内核阶段ms | 基线/执行探针记录数 | 错误 |
| --- | --- | --- | --- | ---: |
| amd64 | 42.20→43.00 | 54.79→44.13 | 70 / 928 | 0 |
| arm64 | 32.07→34.53 | 53.39→35.78 | 72 / 944 | 0 |

SQL采样P99仍有所增加，不能说“没有影响”。IO累计、复查时速率、refault、内存类别和原始节点信号在TEST-RESULTS.json；这些离散点不是连续峰值，agent自身CPU不包含内核辅助进程全部成本。strict检查cgroup可见IO/PSI，不代表已自动识别共享物理磁盘的全部竞争。性能低影响验收仍未通过。可给节点执行器独立的systemd/容器CPU、内存和IO预算，但首版没有自行修改这些配额；评估时应把agent与辅助进程整体计入。

另外保留了普通文件后端>=1GiB回收对照：

| 架构 | 夹具净下降GiB | 达到1GiB门槛耗时s | 最后检查距门槛s | 执行期可见cgroup IO采样最大MiB/s |
| --- | ---: | ---: | ---: | ---: |
| amd64 | 1.125 | 38.11 | 24.52 | 205.29 |
| arm64 | 1.125 | 37.70 | 24.51 | 261.83 |

这项文件实验的SQL/API P99与可见IO峰值上升，**收益门槛通过，低影响未通过**；共享可见cgroup不能逐进程归因。数据完整SHA256和OOM前后计数也已核对。不能把文件后端的1.125GiB结果混成内核后端单次释放1GiB。

## 94/171状态及未完成事项

本轮没有连接171。94仅只读能力检查：5.14.0-611.54.3.el9_7.x86_64、cgroup2fs、memory.reclaim存在、无PSI，时点MemAvailable约7.96GiB；未开写权限探针、未执行回收或更换运行程序。接口存在不证明agent实际权限、SCC/SELinux资格和业务安全。CPU不限、DBS30GiB、HISDBS15GiB、IO40%的既有设置未在本轮改动。

| 待验证项 | 为什么仍重要 |
| --- | --- |
| 生产schema2采集器与真实kubelet/allocatable口径 | 原schema1不能直接冒充新契约；必须有原始时间和实际驱逐配置 |
| 94无PSI真实物理盘与SQL/API替代资格 | 本轮只实现并单测契约，不能在缺少信号时宣称自动救援生效 |
| >=4GiB缓存池与更大单次请求 | 本次内核真实请求是256MiB，不能外推到1GiB或十几GiB |
| mmap热点、父级/脏页压力的真实混合负载 | 单元保护案例不是现场端到端影响结论 |
| 两库/两备份真实等压、校验、恢复、故障及48小时 | 不能由短时独立文件试验推断不被驱逐 |
| OpenShift/SELinux/运行时权限、ARM64 64KiB页 | 原生4KiB页与普通VM权限结果不代表全部部署环境 |

即使已经配置，OOM历史、错误率、未知/过期信号、swap、脏页或IO等保护仍可能否决新请求。已经到hard驱逐线或Node.MemoryPressure为真，首版停止投机操作并要求外部处置；这是提前预警机制，不承诺临门抢救一定成功。UNKNOWN不自动清理，不通过重启数据库掩盖问题。
