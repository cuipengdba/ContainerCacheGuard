# 备份格式、恢复时间和回退

本文说明可执行流程和时间预算。真实规模的最终 RTO 以测试报告为准，不能把理论复制时间写成实测恢复时间。

## 先确定哪一种恢复目标

| 方案 | 日常成本 | 事故时的主要步骤 | 适用考虑 |
| --- | --- | --- | --- |
| 本地普通目录完整备份 | 容量较大、备份 IO 多 | 校验、准备独立恢复目录、回放 WAL、启动和业务核对 | 依赖少，容易演练，当前两端缓存控制的推荐格式 |
| 本地原生增量链 | 通常减少复制数据，仍需扫描元数据及保留父链 | 校验父链、合并、校验合成结果、启动恢复 | 限制链长，不能把增量目录直接当 PGDATA |
| 提前合成完整备份 | 把合并及校验移到正常时段，额外占空间和 IO | 使用已准备完整副本，启动与核对 | 需要快恢复时优先考虑；明确合成时间点对应的 RPO |
| 压缩 tar | 较省空间，增加 CPU 和打包成本 | 下载或定位归档、解压、校验、回放和启动 | 长期保存或异地副本可用；当前不提供源端进度缓存保护 |
| 远端仓库作为唯一备份 | 本地容量少，依赖网络和远端服务 | 拉取、可能解压，再合并、校验和启动 | 网络恢复时间计入 RTO；不适合把快恢复建立在未知网络吞吐上 |
| 专用备用实例 | 持续同步和独立运行成本 | 受控切换、核对复制位置及业务路由 | 通常更适合分钟级 RTO；不能替代独立备份和误删除恢复 |

普通目录备份在物理恢复前仍有配置、认证、扩展版本、文件权限和 WAL 等要求。静态客户端不包含数据库服务端及其业务扩展。[PG18 备份说明](https://www.postgresql.org/docs/18/app-pgbasebackup.html)

## 为什么低限速和 24 小时窗口可能冲突

设完整数据量为 S，复制和校验都采用读速率 R。当前推荐模式在复制后串行做完整文件与 WAL 校验，所以理想下限接近 `2 × S / R`，还要加入准备、检查点、WAL、元数据、写回和暂停。这个估算不意味着设备物理 IO 只有两份：同盘至少涉及源读取、目的写入、校验再读取，约三份数据量，实际还受缓存与文件系统影响。

例如 1.5 TiB：

| 相同的复制/校验读上限 | 单次传输理论时间 | 传输加一次完整读取校验的理论时间 |
| --- | --- | --- |
| 20 MiB/s | 约 21.85 小时 | 约 43.69 小时 |
| 32 MiB/s | 约 13.65 小时 | 约 27.31 小时 |
| 64 MiB/s | 约 6.83 小时 | 约 13.65 小时 |

因此，1.5 TiB 在 24 小时内连同这两阶段完成，理论平均读速率至少约 36.4 MiB/s，实际应更高。业务只能承受更低负载时，要通过增量、专用备用库、独立设备、调整全量周期等办法减少争用；不能同时承诺任意低限速、全量完整校验和固定窗口。配置示例的 20 MiB/s 只是示例，不是这份数据量已验收的值。

## 推荐的恢复准备流程

1. 定期完成全量备份，后续按计划做原生增量，持续保留父清单及其完整链。
2. 备份完成执行文件与 WAL 校验，保存退出码、清单标识和结果记录。只有命令退出 0 还不等于已经证明能实际启动。
3. 在正常时段合成一个新的完整恢复目录，合并前检查父链，合并后再校验。
4. 使用单独的演练副本启动数据库，核对服务器及扩展版本、全部业务对象、关键业务查询和所需数据时间点，随后安全停止演练实例。
5. 保留独立的已验证备份原件、最近合成点及上一条可用链。不要让演练实例直接修改唯一的备份目录。

```sh
./pgcacheguard -config /etc/pgcacheguard.json combinebackup --clone \
  -o /restore/prepared-20261106 \
  /backup/pg18/full-001 \
  /backup/pg18/incr-002 \
  /backup/pg18/incr-003
```

`--clone` 要求当前文件系统支持相应克隆功能，且相关文件位于兼容的文件系统上；不支持时上游可能失败。它可以减少复制工作，不能跳过本工具前后校验，也不能把不同挂载点或远端存储都当作能瞬间克隆。不要把“reflink 创建目录很快”误写成“完整恢复和业务恢复一样快”。[PG18 合并工具说明](https://www.postgresql.org/docs/18/app-pgcombinebackup.html)

## 事故时怎样恢复

先确认原数据库状态和恢复时间点，检查备份链、容量、依赖的服务端镜像与扩展、UID 和目标目录。推荐恢复到一个新的独立目录，验证后由编排流程停旧实例、切换挂载或服务地址，并检查业务。

本工具默认不覆盖 PGDATA。兼容既有 DBS 的直接目标时，需要显式设置 `allow_stopped_pgdata_restore=true`，并满足停库、无 postmaster.pid、目标为空和 Socket 不监听。工具先在相邻 staging 合并和校验，再禁止覆盖地原子发布；已有数据、并发创建目标、挂载点不能改名或权限不足都会失败并保留 staging。

这不替代编排层的停库确认。数据库由外部管理程序自动拉起时，必须先在该管理程序中阻止自动启动；仅看到某个 Socket 不存在不能保证稍后不会启动。工具不会擅自关闭业务服务。

## 出错怎样退回

- 校验或合并失败：保留原链和失败记录，目标不能登记为可恢复成功；选择另一条已验证链，或修复存储/父链后在新目标重试。
- staging 发布失败：根据收据中的 `restore_work_directory` 找到已构建副本，先核实其校验状态和当前数据库是否已启动，再由运维处理；不要循环删除 PGDATA。
- 新实例启动或业务核对失败：先停止新实例，保留日志，按切换前保存的卷/目录和服务路由回退。不要同时对同一 PGDATA 启动两个写实例。
- 控制器因资源压力退出：保持业务优先，降低备份负载或调整时间窗；不得通过关闭监控来把失败强行改成成功。

当前工具不负责备份保留策略、远端传输、Python 压缩线程、服务路由或数据库进程编排。现有 DBS 对旧 PGDATA 的异步压缩可能与恢复竞争资源，这部分必须单独限资源或改调度；直接替换命令不能自动约束父 Python 进程。

## RTO 验收怎样计时

从操作员决定恢复的时刻开始，到业务查询通过并可接流量结束。分别记录：定位备份、下载、解压、父链校验、合并、结果校验、权限/配置准备、WAL 回放、启动和业务验证。预合成的准备成本另列，但其可用性和时间点必须提前演练。

事故恢复如果临时放宽 IO 限制，应使用事先验收的恢复配置并评估同机其他业务；不能在同盘仍承载关键业务时简单取消所有限制。低备份负载与快恢复可使用不同的经过验证的资源预算，但当前默认配置不会自动推断哪一个业务可以牺牲。
